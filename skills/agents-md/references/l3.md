# L3 워크플로우

L3는 git 저장소 또는 모노레포 루트의 운영 규칙. 저장소 수만큼 존재. 비모노레포면 L3가 최하위.

## Analyst 역할

- `target_path/.git` 확인 — 없으면 경고 (사용자가 잘못된 경로 지정했을 가능성)
- 자식 디렉토리 enumerate + 각 폴더 분류
- 모노레포 휴리스틱 적용 (layer-detection.md 참조) → monorepo / single project / 불확실 판단
- 각 자식 폴더의 역할 추정:
  - README.md의 첫 단락 1줄 요약
  - package 파일의 키워드 (name, description)
  - 폴더 이름 패턴 (`*-mcp`, `*-api`, `web-*` 등)
- 루트 공통 설정 파일 enumerate:
  - lockfile (`package-lock.json`, `pnpm-lock.yaml`, `yarn.lock`, `poetry.lock`, `Cargo.lock`, `go.sum`)
  - workspace 설정
  - lint/format 공통 설정 (`.eslintrc*`, `.prettierrc*`, `pyproject.toml`의 ruff/black)
  - TypeScript/Python 공통 설정
  - Docker 공통 설정
  - CI/CD 파일
- 부모 AGENTS.md (L1/L2) 확인 → Writer가 중복 회피

## 분기: 모노레포 vs 비모노레포

### 모노레포 L3
- 본문에 서브폴더 인덱싱 + 공통 운영 규칙만
- L4가 따로 존재할 것이라 가정 → 실행/테스트/빌드 명령은 "각 L4 참조" 수준
- 가이드 351~431행 형식 따름

### 비모노레포 L3 (= 최하위)
- 본문에 L4 수준의 디테일까지 포함 (실행/테스트/빌드/배포)
- 자식 폴더는 단순 폴더 설명만
- 가이드 477~607행의 L4 권장 내용도 부분 흡수

## 인터뷰 질문 (8개)

### Q1. 저장소 목적

**추천:** Analyst 분석 + README 기반 추정 (예: "Jenkins, Slack 자동화, 영상 변환 등 빌드/운영 자동화 도구 모노레포")
**출처:** 코드 (README, package.json description)
**도구:** plain text (자유 서술)

### Q2. 모노레포 여부

**추천:** Analyst 판단값
**출처:** 코드 (휴리스틱)
**선택지:** A. 모노레포 / B. 단일 프로젝트 (L3 최하위) / C. 불확실 (인터뷰 진행하며 결정)

### Q3. 서브폴더 간 독립성 수준 (모노레포만)

**추천:** "각 하위 폴더는 가능한 한 독립 프로젝트로 취급"
**출처:** 가이드 373행
**선택지:** A. 완전 독립(추천) / B. 일부 공유 (공통 유틸 등) / C. 강한 결합

### Q4. 루트 설정 변경 기준

**추천:**
```text
다음 파일은 저장소 전체 영향 — 수정 전 영향 범위 확인:
- workspace 설정 / lockfile / CI/CD 설정 / Docker 공통 / lint/format 공통 / TypeScript/Python 공통
```
**출처:** 가이드 409~416행 + Analyst 발견 파일 목록
**선택지:** A. 권장값(추천) / B. 더 엄격(모든 루트 파일 승인) / C. 자유롭게 변경

### Q5. 새 서브 프로젝트 추가 기준 (모노레포만)

**추천:**
```text
1. 기존 폴더와 목적이 겹치지 않는가
2. naming convention이 맞는가
3. 루트 workspace에 등록 필요한가
4. 독립 README 또는 AGENTS.md 필요한가
5. 테스트/빌드 방법이 명확한가
```
**출처:** 가이드 420~426행
**선택지:** A. 권장 체크리스트(추천) / B. 단순화 / C. 항상 사용자 결정

### Q6. CI/CD 영향 범위

**추천:** Analyst가 발견한 워크플로 파일 목록 + "수정 시 관련 pipeline 영향 범위 설명"
**출처:** 코드 (`.github/workflows/*` enumerate)
**도구:** plain text

### Q7. 공통 dependency 관리 방식

**추천:** "공통 유틸은 2개 이상의 실제 사용 사례가 생긴 뒤 고려, 먼저 서브 내부에서 단순 해결"
**출처:** 가이드 377~378행
**선택지:** A. 권장값(추천) / B. 적극적 공통화 / C. 절대 공통화 안 함

### Q8. 위험 영역

**추천:** Analyst가 발견한 민감 파일 + lockfile 등
**출처:** 코드 + 가이드 428행
**도구:** plain text (사용자 자유 추가)

### Q9 (비모노레포 L3에 추가)

비모노레포면 다음을 추가로 질문:
- 실행 방법 — Analyst 발견값 추천
- 테스트 방법 — Analyst 발견값
- 빌드 방법 — Analyst 발견값
- 배포 방법 — plain text
- 외부 API 사용 여부 — Yes/No
- mock/dry-run 규칙 — plain text

## Writer 입력 (템플릿)

`references/templates/l3-template.md`.

핵심 섹션 (가이드 354~431행):
1. 저장소 목적

4. 작업 전 확인
5. 공통 명령어 (있을 때만)
6. 검증 기준
7. 루트 설정 변경 기준
8. 새 서브 프로젝트 추가 기준 (모노레포만)
9. 주의사항

비모노레포면 추가로:
10. 실행/테스트/빌드/배포
11. 외부 연동 / mock 규칙
